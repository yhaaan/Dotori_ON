# 한글 주석 스타일 가이드

주석을 쓰는 방식에 대한 규칙이다. 사람과 AI 모두 이 문서를 기본 규칙으로 사용한다. 현재 요청의 명시적인 지시가 이 문서보다 우선한다.

---

## 1. 대원칙 — 코드가 못 하는 말만 쓴다

코드는 **무엇을 하는지**를 이미 말하고 있다. 주석은 **왜 그렇게 했는지**를 쓴다.

```csharp
❌ // 골드를 지급한다
   gold.Gain(_skipRewardGold);

⭕ // 태우고 넘긴 보상은 골드로 대체 지급합니다. 연출은 클리어 파이프라인(CoResolveRoundClear)이
   // 선택 완료 후 남은 pending을 재생하는 방식으로 클리어 골드와 동일하게 처리됩니다.
   private void GrantSkipGold()
```

주석을 쓸지 말지 판단하는 기준은 하나다. **6개월 뒤의 내가 이 줄을 보고 "왜 이렇게 짰지?" 하고 멈출 것 같은가.** 멈출 것 같으면 쓴다.

특히 다음은 반드시 남긴다.

- **직관에 어긋나는 순서·조건** — `// TakeDamage는 OnDamaged 발화 후에 사망을 검사하므로 여기서 복구하면 OnDead가 발동하지 않는다.`
- **다른 코드와의 암묵적 계약** — `// AddRelic은 Initialize 이후에 인스턴스를 컨트롤러 목록에 넣으므로,`
- **예외 상황을 일부러 그렇게 둔 이유** — `// 카메라 컨트롤러가 없는 예외 상황에서는 안내 자체가 누락되지 않도록 즉시 표시합니다.`
- **호출 규약** — `// 위치 세팅 이후에 호출할 것. delay는 순차 팝업용 지연 시간.`
- **임시 처리 · 나중에 옮길 것** — 3.4의 TODO 형식으로.

---

## 2. 언어

- **한글로 쓴다.** 문장은 한글, 단어는 정확하게.
- **타입명 · 메서드명 · 필드명은 영문 그대로** 쓴다. 번역하거나 음차하지 않는다.
  - ⭕ `// ResolveAttackMode는 보드/플레이어 상태만 조회하므로 안전합니다.`
  - ❌ `// 리졸브어택모드는 ...`
- **자리잡은 외래 기술 용어**는 영문으로 쓴다. `Presenter`, `Pre-Dash Tell`, `pending`, `best-effort` 등. 억지로 한글화하지 않는다.
- **게임 내 개념은 한글**로 쓴다. `유물`, `보상 풀`, `턴 막대`, `패링`.

## 3. 주석의 종류와 쓰임

### 3.1 `/// <summary>` — 밖에서 쓰는 사람을 위한 설명

**존댓말(`~합니다` / `~입니다`)로 쓴다.** 이 프로젝트의 XML 주석 대부분이 이 어투다.

붙이는 대상:

- `public` / `internal` 타입 — 클래스, 인터페이스, 열거형
- 밖에서 호출하는 메서드 중 이름만으로 계약이 안 드러나는 것
- 의미가 이름에 안 담기는 직렬화 필드

```csharp
/// <summary>
/// 유물 보상 선택 흐름을 View와 연결하는 Presenter입니다.
/// </summary>
public sealed class RelicRewardPresenter : IUIManagedPresenter
```

규칙:

- **한 문장**으로 끝낸다. 길어지면 첫 문장에 결론을 두고 다음 문장에 조건을 붙인다.
- 이름을 그대로 풀어쓰지 않는다. `/// 플레이어를 초기화합니다.` 를 `InitializePlayer()` 위에 쓸 이유는 없다.
- 파라미터를 언급할 때는 `<paramref name="..."/>` 를 쓴다.
  - `/// 동의 시 <paramref name="onAgree"/>, 거부/ESC/빈 공간 클릭 시 <paramref name="onCancel"/>가 호출됩니다.`
- `<param>`, `<returns>` 를 형식적으로 채우지 않는다. `<summary>` 한 줄로 다 설명되면 그걸로 끝낸다.

### 3.2 `//` 줄 주석 — 안에서 읽는 사람을 위한 설명

**평서체(`~한다` / `~이다`)와 존댓말 중 하나를 고르되, 한 파일 안에서는 섞지 않는다.**

- **코드 바로 위 줄**에 붙인다. 사이에 빈 줄을 넣지 않는다.
- 설명 대상 코드와 **같은 들여쓰기**로 맞춘다.
- 두 줄이 넘어가면 문장을 자연스럽게 이어 쓴다. 각 줄을 `//` 로 시작하되, 문장을 억지로 한 줄에 맞추려 줄이지 않는다.

```csharp
// 본문 토큰은 모든 선택지의 토큰을 합친 것입니다. 같은 토큰 이름을 여러 선택지가 쓰면 마지막 값이 남으므로,
// 선택지 순서를 바꾸면 본문 표기도 바뀝니다.
```

### 3.3 꼬리 주석 — 값의 의미만

같은 줄 끝에 붙이는 주석은 **상수 · 튜닝 값의 의미**를 밝힐 때만 쓴다. 로직 설명에는 쓰지 않는다.

```csharp
⭕ private const float DashAngle = 12f;        // 수평 돌격 시 눕히기 각도
⭕ private const float FlyDuration = 0.38f;    // 선형 감쇄

❌ if (relic == null) return;                  // 유물이 없으면 반환한다
```

- 코드와 `//` 사이에 공백을 두되, 줄마다 칸을 맞추려고 공백을 정렬하지 않는다. 값이 하나 바뀌면 전 줄이 diff에 잡힌다.
- 명사구로 짧게 끝낸다. 문장을 쓸 거면 윗줄 주석으로 올린다.

### 3.4 TODO

**`// TODO(범위): 내용` 형식으로 통일한다.**

```csharp
// TODO(text-enrichment): 키워드 색상/아이콘/Febucci 애니메이션용 RichText 데코레이션 파이프라인 예정.
```

- `범위` 는 이 TODO가 속한 작업 단위나 시스템 이름이다. 검색해서 한 번에 모을 수 있게 하는 것이 목적이다.
- **무엇을 해야 하는지**를 쓴다. `// TODO: 개선 필요` 는 아무것도 알려주지 않는다.
- 당장 고칠 수 있으면 TODO를 쓰지 말고 고친다.
- `FIXME`, `HACK`, `XXX` 는 쓰지 않는다. TODO 하나로 통일한다.

## 4. 구역 나누기

### 4.1 튜닝 상수 블록

인스펙터에 노출하지 않고 코드에서만 만지는 연출 수치는 한 곳에 모으고 머리말을 붙인다.

```csharp
// ---- 연출 튜닝 확정값 (코드에서만 수정) ----
private const float FlyDuration = 0.38f;
private const Ease FlyEase = Ease.InBack;
private const float AnticipationRise = 28f;
```

`(코드에서만 수정)` 이 핵심이다. 이 값을 인스펙터에서 찾다가 시간을 버리는 일을 막는다.

### 4.2 섹션 구분선

파일이 길어져 성격이 다른 메서드 묶음이 생기면 구분선으로 나눈다. **형식을 하나로 고정한다.**

```csharp
// ---------------- 보드 조회 헬퍼 ----------------
```

- 대시는 **양쪽 16개**, 제목은 가운데. 길이를 제각각 두지 않는다.
- 구분선이 **네 개를 넘으면** 그 파일은 나눠야 한다는 신호다. 주석으로 버티지 말고 클래스를 분리한다.
- `#region` 은 쓰지 않는다. 접힌 코드는 안 읽히고, 접힌 채로 썩는다.

## 5. 쓰지 않는 주석

- **코드를 그대로 옮긴 주석** — `// i를 1 증가시킨다`
- **주석 처리한 죽은 코드** — 지운다. 되살릴 일이 있으면 git에서 꺼낸다.
- **서명 · 날짜** — `// 2026-08-27 홍길동 수정`. 이건 git이 하는 일이다.
- **파일 머리 배너** — 파일명, 작성자, 개요를 나열한 헤더 블록. 클래스 위 `<summary>` 하나면 된다.
- **감정 · 잡담** — `// 이거 왜 되는지 모르겠음`. 모르겠으면 그 사실을 TODO로 남긴다. 무엇을 확인해야 하는지와 함께.

---

## 6. 주석은 코드와 같이 고친다

**틀린 주석은 없는 주석보다 나쁘다.** 없는 주석은 코드를 읽게 하지만, 틀린 주석은 코드를 안 읽게 만든다.

- 코드를 고치면 **그 위 주석을 반드시 다시 읽는다.** 여전히 맞는 말인지 확인한다.
- 주석이 가리키는 다른 타입·메서드 이름을 바꿨다면, 그 이름을 언급한 주석을 전부 찾아 고친다.
- 리뷰할 때 코드와 주석이 어긋나 있으면 그 자리에서 고친다. 다음으로 미루지 않는다.

---

## 7. 체크리스트

- [ ] 코드를 그대로 반복하지 않고, 왜인지를 쓰고 있는가
- [ ] `<summary>` 는 존댓말, 한 문장인가
- [ ] 타입·메서드 이름을 영문 그대로 썼는가
- [ ] 주석이 설명하는 코드 바로 위 줄에, 같은 들여쓰기로 붙어 있는가
- [ ] TODO가 `TODO(범위): 무엇을` 형식인가
- [ ] 주석 처리된 죽은 코드나 서명이 남아 있지 않은가
- [ ] 코드를 고쳤다면 위 주석도 다시 읽었는가
