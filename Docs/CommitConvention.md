# Project-CSP 커밋 컨벤션

커밋 메시지를 작성할 때 따르는 규칙이다. 사람과 AI 모두 이 문서를 기본 규칙으로 사용한다. 현재 요청의 명시적인 지시가 이 문서보다 우선한다.

---

## 1. 기본 형식

```
<이모지>[라벨] 제목

* 설명 1
* 설명 2
```

- **제목 줄** — `이모지` + `[라벨]` + 공백 하나 + 제목. 이모지와 대괄호 사이에는 공백을 넣지 않는다.
- **본문** — 필요할 때만 쓴다. 제목 줄과 한 줄 띄우고, `* ` 불릿으로 항목을 나열한다.
- 한 커밋에는 한 가지 변경만 담는다. 라벨을 두 개 붙여야 할 것 같으면 커밋을 나눈다.

예시

```
✨[Feat] 설정창 UX 개편

* 탭 선택 표시 추가
* 설정 항목 한 줄 전체를 토글 클릭 영역으로
* 볼륨 슬라이더에 퍼센트 표기
* 열기/닫기, 탭 전환 연출을 SettingsWindowAnimator로 분리
```

## 2. 라벨

| 라벨 | 설명 | 작성 기준 |
| --- | --- | --- |
| ✨ **[Feat]** | 새로운 게임 시스템, 메카닉, 컨텐츠 추가 | 제목 → 기능 설명 |
| ⚙️ **[Core]** | 백엔드, 프레임워크, 도구, 시스템 기반 작업 | 제목 → 기능 설명 |
| 🐛 **[Fix]** | 명백한 오류(버그)의 수정, 기획 의도와 다른 동작 해결 | 제목 → 현상<br>설명 → 수정 방법 |
| ♻️ **[Refactor]** | **기능 변경 없이** 코드의 구조만 개선 | 제목 → 구조 개선 내용 |
| 🗺️ **[Design]** | 레벨 디자인, 밸런싱, 수치 조정 | 제목 → 현상<br>설명 → 수정 방법 |
| 🩹 **[Patch]** | 사소한 프리팹/씬 변경, 오타 수정, 단순 수치 조정 | 제목 → 현상<br>설명 → 수정 방법 |
| 🗃️ **[Update]** | 데이터베이스 관련 업데이트 | |
| 🎨 **[Asset]** | 비주얼 에셋, 사운드, 애니메이션 추가 및 수정 | |
| 📝 **[Docs]** | 문서 수정 (README, 기획서, 주석) | |
| 🧹 **[Chore]** | 빌드 설정, 패키지 관리, git 설정, 파일 이동, 폴더 구조 변경 | |
| 🔀 **[Merge]** | 브랜치 합병 | |
| 🔥 **[Del]** | 기능 제거 | |
| 🎉 **[Init]** | 초기 커밋 | |
| 💚 **[Build]** | 빌드 파일 생성 | 제목 → 버전 표기 |

### 2.1 헷갈리는 라벨 구분

- **[Feat] / [Core]** — 플레이어가 게임에서 체감하는 것이면 `[Feat]`, 그 아래를 받치는 구조·설정·개발 도구면 `[Core]`.
  - `✨[Feat] 포션시스템 구현` / `⚙️[Core] NodeTypeConfigSO 추가, 새로운 아이콘 적용`
- **[Fix] / [Patch]** — 잘못 동작하던 것을 고쳤으면 `[Fix]`, 멀쩡히 동작하지만 손본 사소한 변경이면 `[Patch]`.
  - `🐛[Fix] 화로 이벤트 100% 선택지 보이는 현상 수정` / `🩹[Patch] 체력 텍스트 색 빨간색으로 변경`
- **[Design] / [Patch]** — 밸런스 의도를 갖고 수치를 조정했으면 `[Design]`, 위치·오타 같은 단순 손질이면 `[Patch]`.
- **[Refactor]** — 동작이 조금이라도 달라졌다면 `[Refactor]`가 아니다. `[Feat]`이나 `[Fix]`로 쓴다.
- **[Asset]** — 에셋 파일 자체를 추가·교체한 커밋에 쓴다. 에셋을 쓰는 코드까지 함께 바뀌었으면 그 코드 쪽 라벨을 쓴다.

## 3. 제목 작성

- **한국어**로, **50자 안쪽**으로 쓴다.
- 마침표로 끝내지 않는다.
- 무엇을 했는지 결과가 드러나게 쓴다. `수정`, `변경`, `추가` 같은 단어만 있는 제목은 피한다.
  - ❌ `🩹[Patch] UI 수정`
  - ⭕ `🩹[Patch] 골드 아이콘 stat으로 교체`
- `[Fix]`, `[Design]`, `[Patch]`는 **현상**을 제목에 쓴다. 고친 방법은 본문에 쓴다.
  - `🐛[Fix] 태그 숫자값 우하단 표시`

---

## 4. 본문 작성

본문은 선택이지만, 다음 경우에는 쓴다.

- 변경 항목이 둘 이상일 때 — 항목마다 불릿 하나.
- `[Fix]`, `[Design]`, `[Patch]`에서 **어떻게 고쳤는지**를 남겨야 할 때.
- 임시 처리, 하드코딩, 추후 정리가 필요한 부분 — 나중에 찾을 수 있게 반드시 남긴다.

예시

```
🗺️[Design] 어두워지는 특수전투 밸런스 조정

* 최초 시야 수치 6 -> 7
* 최소 시야 수치 1 -> 1.5
```

```
✨[Feat] 포션시스템 구현

* 현재는 미지 선택지 용만 있음, 설명 스크립트에 하드코딩 추후 구조 분리 필요
* 디버그 기능 있음
```

## 5. 머지 커밋

브랜치를 합칠 때는 `🔀[Merge]`를 붙인다.

```
🔀[Merge] Merge branch 'dev' of https://github.com/DotoriDoguldan/Project-CSP into dev
```

git이 자동 생성한 머지 메시지에도 라벨을 붙여 준다.

## 6. 체크리스트

커밋 전에 확인한다.

- [ ] 이모지와 라벨이 짝이 맞는가
- [ ] 한 커밋에 한 가지 변경만 담겼는가
- [ ] 제목만 읽고 무엇이 바뀌었는지 알 수 있는가
- [ ] 수정 방법이나 임시 처리를 본문에 남겼는가
